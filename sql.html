SQL Things You Need to Know

SQL is one of the first tools I reach for when I need to pull data, connect sources, and understand what the numbers are telling me. You don't need every SQL command to get started. These are the patterns I find most useful in real analytics work.

A practical field guide

Start with a question, then build the query.

Think of SQL as a way to ask your data questions. In the examples below, we'll use fictional patients and visits tables. The syntax is broadly applicable, though small details vary across SQL databases.

01

SELECT, FROM & WHERE: Start With the Data You Need

Pick columns, choose a table, and filter rows.

This is where I start almost every analysis. SELECT chooses columns, FROM identifies the table, and WHERE filters records before any grouping happens.

SELECT patient_id, visit_date, diagnosis_code
FROM visits
WHERE visit_date >= '2026-01-01'
  AND diagnosis_code IS NOT NULL;

You will often see SELECT * when exploring an unfamiliar table. It returns all columns, which is convenient for a quick look.

SELECT *
FROM visits;
My tip: Use SELECT * to explore, but choose only the columns you need for repeatable analyses. It makes queries clearer and avoids moving unnecessary data.
02

JOIN: Connect Tables Using a Shared Key

The three joins I find most useful are INNER, LEFT and FULL.

Real datasets rarely contain everything in one table. A JOIN connects records through a shared field, such as patient_id. Here, patients is our starting table and visits contains visit records.

JoinWhat you keepWhen I use it
INNER JOINOnly matching rows from both tablesPatients who have visit records
LEFT JOINAll rows from the left table, plus matching right-side rowsAll patients, including those without a visit
FULL OUTER JOINAll rows from either table, matched where possibleCheck which IDs exist in one source but not the other
SELECT p.patient_id, p.region, v.visit_date
FROM patients AS p
LEFT JOIN visits AS v
  ON p.patient_id = v.patient_id;

Change LEFT JOIN to INNER JOIN to keep matched records only. Use FULL OUTER JOIN to retain unmatched records from both sides (where supported by your SQL database).

My tip: Check the level of detail before joining. If one patient has five visits, a patient-to-visits join produces five rows for that patient. A join can multiply rows and inflate totals if you are not careful.
03

SUM, AVG & COUNT: Get Useful Numbers

Turn many records into totals, averages and counts.

These are the aggregations I use most often. They answer questions such as “How much?”, “What is typical?” and “How many?”

SELECT
  COUNT(*) AS number_of_visits,
  SUM(allowed_amount) AS total_allowed,
  AVG(allowed_amount) AS average_allowed
FROM visits
WHERE allowed_amount IS NOT NULL;

COUNT(*) counts rows, while COUNT(column_name) counts non-null values in that column. SUM and AVG also ignore null values.

My tip: Always be clear about what a row represents. Counting visit rows is not the same as counting unique patients. For unique patients, use COUNT(DISTINCT patient_id).
04

GROUP BY: Compare Categories

Break down metrics by region, month or another dimension.

After I calculate an overall total, my next question is often: how does it differ by group? GROUP BY gives one summary row per group.

SELECT
  region,
  COUNT(*) AS patient_count
FROM patients
GROUP BY region;

To summarize visit activity by patient, for example:

SELECT
  patient_id,
  COUNT(*) AS visit_count,
  SUM(allowed_amount) AS total_allowed
FROM visits
GROUP BY patient_id;

To filter groups after aggregation, use HAVING rather than WHERE:

SELECT patient_id, COUNT(*) AS visit_count
FROM visits
GROUP BY patient_id
HAVING COUNT(*) >= 2;
My tip: WHERE filters individual rows before grouping; HAVING filters the grouped results. When combining tables, check for duplicated rows before calculating totals.
05

ORDER BY: Put the Important Results First

Sort summaries so patterns are easier to spot.

Sorting is simple but incredibly useful. I often sort descending to identify the largest groups, then investigate why they stand out.

SELECT region, COUNT(*) AS patient_count
FROM patients
GROUP BY region
ORDER BY patient_count DESC, region ASC;

DESC sorts highest to lowest, while ASC sorts lowest to highest. You can sort on more than one column.

My tip: Without an ORDER BY, SQL does not guarantee the order of returned rows—even if the results seem sorted today.
06

ROW_NUMBER(): Choose One Record Per Group

A window function I use constantly for latest records and ranking.

This is one of the most useful SQL patterns to learn after the basics. ROW_NUMBER() assigns a sequence number within each group, without collapsing the original rows.

SELECT
  patient_id,
  visit_date,
  visit_id,
  ROW_NUMBER() OVER (
    PARTITION BY patient_id
    ORDER BY visit_date DESC, visit_id DESC
  ) AS visit_rank
FROM visits;

PARTITION BY patient_id starts the numbering over for each patient. ORDER BY visit_date DESC puts the latest visit first. Adding visit_id DESC makes the ranking consistent when dates tie, assuming visit IDs are unique.

To keep only the latest visit per patient, I use a common table expression (CTE):

WITH ranked_visits AS (
  SELECT
    patient_id, visit_id, visit_date,
    ROW_NUMBER() OVER (
      PARTITION BY patient_id
      ORDER BY visit_date DESC, visit_id DESC
    ) AS rn
  FROM visits
)
SELECT patient_id, visit_id, visit_date
FROM ranked_visits
WHERE rn = 1;
My tip: Choose an ORDER BY that handles ties, especially when selecting a “latest” record. Without a unique tie-breaker, the row ranked first may not be consistent.
07

A Few Habits That Make SQL More Reliable

Small checks can prevent big mistakes.

  • Know your grain: is each row a patient, visit, claim, or transaction?
  • Check joins: compare row counts and unique IDs before and after joining.
  • Handle nulls intentionally: use IS NULL and IS NOT NULL, not = NULL.
  • Use readable names: table aliases and clear output column names help you review a query later.
  • Validate your totals: compare a few records and group summaries to what you expect.
My tip: Start with a small result you can verify. Build the query one step at a time instead of writing everything at once.
Where I would start

A simple path to useful SQL

  1. SELECT / WHERE — find the records you need.
  2. JOIN — connect related data.
  3. COUNT / SUM / AVG — calculate key metrics.
  4. GROUP BY — compare categories.
  5. ORDER BY — prioritize what stands out.
  6. ROW_NUMBER() — rank records within a group.

With these building blocks, you can answer many common analytics questions. Focus on understanding the data and validating the results—not memorizing syntax.
